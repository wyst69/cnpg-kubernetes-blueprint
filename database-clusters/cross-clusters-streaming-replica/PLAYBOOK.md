# Cross-clusters Bidirectional Streaming Replication Setup

This folder contains a production-grade, highly available dual-cluster topology spanning two namespaces (`main` and `dr`) with automated quorum matching via `method: first` and complete Mutual TLS (mTLS) authentication.
The same mechanisms can be be used across two different k8s clusters sitting in two different data centers.

## 🔐 Prerequisites: The two clusters MUST have access to the same S3-compatible bucket

## Deploying the clusters

### Step 1: Deploy the main cluster (`pg-main`)
```bash 
kubectl apply -f pg-main.yaml
```

### Step 2: Copy the `main` secrets in the `dr` namespace
- `pg-main-replication` & `pg-main-ca` (Generated by CNPG)

Before copying them, they should be stripped down to the minimum to make sure CNPG doesn't mess with them.
Example:
``` yaml
apiVersion: v1
data:
  ca.crt: LS0tLS1CRUdJTiBDRVJUSUZJQ0FURS0tLS0t...   # <-- truncated: use pg-main's own ca.crt
kind: Secret
metadata:
  labels:
    app.kubernetes.io/managed-by: cloudnative-pg
  name: pg-main-ca
  namespace: dr
type: Opaque
```

### Step 3: Deploy the dr cluster (`pg-dr`)
```bash 
kubectl apply -f pg-dr.yaml
```

### Step 4: Copy the `dr` secrets in the `main` namespace
- `pg-dr-replication` & `pg-dr-ca` (Generated by CNPG)

### Step 5: check the cluster status and the replication status with the cnpg plugin 

```bash 
kubectl cnpg status pg-main -n main

kubectl cnpg status pg-dr -n dr

kubectl cnpg psql pg-main -n main -- -c "select application_name, sync_state from pg_stat_replication"
```

pg-main should be primary

pg-dr should be designated primary

pg-dr and one local replica should be in sync with pg-main

## ⚡ The Switchover

The architecture is explicitly designed to be fully symmetrical. Both clusters already hold the connection blueprints for one another. Initiating a controlled switchover or recovering from a failover is completely declarative.
Note: each operation takes a couple of minutes to complete.

### Current State (Normal Operations)
- `pg-main` is the global primary (`replica.primary: pg-main`).
- `pg-dr` is actively streaming from main (`replica.primary: pg-main` and `replica.source: pg-main`).

### Step 1: Demote the main cluster `pg-main`
```yaml
# Inside pg-main.yaml
spec:
  replica:
    primary: pg-dr  # Changed from its own name to-pg-dr
    source: pg-dr
```

```bash 
kubectl apply -f pg-main.yaml
```

This is enough for CNPG to demote the cluster `pg-main`.
When the demotion is complete, CNPG generates a demotion token that we will need to promote `pg-dr`

```bash
kubectl get cluster pg-main -n main -o jsonpath='{.status.demotionToken}'
```

### Step 2: Promote the Disaster Recovery Cluster (`pg-dr`)
To break the replication chain and promote the DR cluster to a read-write primary, update `pg-dr.yaml` to point to itself:

```yaml
# Inside pg-dr.yaml
spec:
  replica:
    primary: pg-dr          # Promoted to global primary
    source: pg-main
    promotionToken: "eyJhbGciOi..."  # <-- Paste the extracted demotionToken here
```

### Step 3: check the cluster status and the replication status with the cnpg plugin 

```bash 
kubectl cnpg status pg-main -n main

kubectl cnpg status pg-dr -n dr

kubectl cnpg psql pg-dr -n dr -- -c "select application_name, sync_state from pg_stat_replication"
```

pg-main should be designated primary

pg-dr should be primary

pg-main and one local replica should be in sync with pg-dr
